## 1. Summary

UPDATE 14 October 2026 (second pass): sections 4b, 5, 6b and 9 are new (primary release notes checked, developer docs read, community known issues searched on GitHub and the forum); the bullets below that touch them are summarised in the last four bullets of this list.

- The official ROOT manual chapter on RooFit is one short page with no fitting-API detail; the real reference material is the Doxygen text in RooAbsPdf.cxx and the tutorials. The 2009 "RooFit Users Manual v2.91" is the only long-form guide and is partly outdated (see section 3).
- Release notes: the big behaviour changes for many small binned extended fits are (a) new vectorised "cpu" backend as default from 6.32, (b) Minuit2 default minimiser from 6.30, (c) Extended() default consistent between fitTo and chi2FitTo in 6.30, (d) NaN-packing/recovery from undefined regions since 6.24 (not in my local notes), (e) RooCrystalBall high-N stability fix in 6.36, (f) `RooFit::Optimize()` only matters for the legacy backend (deprecated in 6.40).
- All the quoted log messages are explained in section 8 with file:line. The "p.d.f value is less than zero, trying to recover" and "top-level p.d.f evaluates to NaN" blocks are one cascade, not two problems, and they are benign if the final fit status is good. They come from Chebychev2_bkg going negative at the edge of the range.
- Tutorial run results (section 6): 12 tutorials ran in this build with rc=0, including rf202 (extended fit), rf614 (binned-fit problems; very relevant), rf502/rf503 (workspace), rf515 (JSON, via PyROOT), hf001. The RooBatchCompute library reports "generic CPU library compiled with no vectorizations" on this macOS arm64 build [verified].
- Practical finding: the "(remaining N messages suppressed)" number over-reports the unprinted messages by 2 (section 8.12).
- (Second pass, 9.1) The developers' diagnosis of Minuit2 status 3 with huge likelihood values is round-off in the NLL: Moneta, 2023: machine limit = epsilon x |NLL| with epsilon ~ 1e-8 (Minuit2 precision), and `Offset(true)` / `Offset("bin")` lowers it; Strategy(2) did not help in the cases found; no developer statement calls status 3 benign. #20083 (Offset ignored by fitTo) is fixed in this build.
- (Second pass, 9.2-9.5) Chebychev negative values: the developers' stance (#12452, 2025) is that clipping to zero does not help in a fit, the NaN-packing recovery is intended, and the cure is a pdf or parameter range that stays positive; RooCrystalBall high-n overflow is fixed in this build (verified to n=1e6), the analytic integral near n=1 has a ~1e-6 relative error here (fixed in 6.38.00 by #19602); SumW2Error(true) gives correct errors for scaled histograms (verified), default and SumW2Error(false) do not, AsymptoticError(true) is within 2% and warns for binned data.
- (Second pass, 4b) The 6.38 and 6.40 release-note claims were verified against the primary files; 6.36.12 and 6.36.14 exist and contain no RooFit or Minuit2 fix; #23221 (HS3 export silently empty while an integral object is alive) reproduces in 6.36.10; the NumCPU multithreading in the cpu backend (PR #23140) is master-only and would not change anything for 100-200 bin fits.

### 2.5 fitTo / createNLL Doxygen text (local, authoritative for 6.36) [source RooAbsPdf.cxx]
Key statements and where the text disagrees with the code:
- RooAbsPdf.cxx:835 `NumCPU`: "Currently, this setting is ignored with the cpu Backend". Consistent with project comment in DynamicRooFitter.h.
- :851-871 EvalBackend: cpu default ("Since ROOT 6.23 ... default" - the text is wrong on the date; release notes say default from 6.32 [doc README/ReleaseNotes/v632/index.md:149]); legacy "might need more than 20 threads to see about 10% gain over cpu"; BatchMode() is "now deprecated".
- :876 `Optimize(bool)` "on by default" - in createNLL the code default is 0 (FitHelpers.cxx:613 `pc.defineInt("optConst","Optimize",0,0)`), in fitTo the MinimizerConfig default is 2 (FitHelpers.cxx:232) [source]. Under the cpu backend the const-term optimisation is a no-op: RooEvaluatorWrapper does not override constOptimizeTestStatistic (grep over roofitcore/src found overrides only in RooAbsOptTestStatistic, RooAbsTestStatistic, RooRealMPFE, RooFuncWrapper(empty)) [source; the "no-op" conclusion is [inferred], not run]. The INFO message "activating const optimization" is still printed.
- :817 `Extended(bool)` "off by default" in createNLL docs, but FitHelpers.cxx:58,609 `extendedFitDefault = 2` = automatic: extended iff pdf can/must be extended, and logs "p.d.f. provides expected number of events, including extended term in likelihood" [source]. The project (extended RooAddPdf with yields) therefore gets the extended term even without Extended(1).
- :915 `IntegrateBins(double)`: <0 deactivated, 0 only for continuous pdf with RooDataHist, >0 everywhere. Code default is -1 (FitHelpers.cxx:621 `defineDouble("IntegrateBins","IntegrateBins",0,-1.)`) so the default is NO bin integration: the pdf is evaluated at bin centres [source].
- :904-912 `Offset("none"|"initial"|"bin")`; "bin" is recommended for numerical stability and makes 2*NLL approximately chi2.
- :1000 `SumW2Error`, :1023 `AsymptoticError`; :1031 `PrefitDataFraction` "may give bad results in binned analysis".
- :975-980 Minimizer default text says "MINUIT/MIGRAD" - outdated: Minuit2 is the default since 6.30 [doc v630 notes]. Minos default off, Hesse on, Save off, Strategy 1, PrintLevel default 1 (-1 suppresses RooFit informational messages) [source RooAbsPdf.cxx:985-1040; FitHelpers.cxx:229-245].
- :1010 `EvalErrorWall(true)` default on; `RecoverFromUndefinedRegions(strength)` default 10 (FitHelpers MinimizerConfig recoverFromNaN = 10) [source].
- `PrintEvalErrors(numErr)` default 10 (RooAbsReal.cxx:1676 for plots; FitHelpers numee) [source]; see 8.12 for the off-by-two.

Key facts and 6.36 accuracy:
- p.15: normalised pdf value = raw / integral; `createIntegral(x, NormSet(x), Range(...))` gives the fraction in a range. Still accurate; this is what DynamicRooFitter uses.
- p.21-23: extended RooAddPdf with N pdfs and N yields; "the extended likelihood term is automatically included" for extended pdfs. Still accurate (matches FitHelpers extendedFitDefault).
- p.22: RooExtendPdf trick to fit the yield in a sub-range directly (errors propagate automatically). Accurate and relevant as an alternative to getPropagatedError.
- p.23-25: RooAddPdf fraction coefficients refer to normalised shapes; `Range()` in fitTo creates a reference range "fit" automatically; SumCoefRange. Still accurate.
- p.10-12: fit output shown is the legacy TMINUIT one; "default fit uses MINUIT, MIGRAD, HESSE" - OUTDATED (Minuit2 default since 6.30, output format differs; fitTo has no Minos by default now: the Appendix E table at p.128 says "Minos on by default", the 6.36 Doxygen says off) [doc vs source].
- p.127-128 Appendix E: "NumCPU(int): parallelize NLL calculation", "Optimize(Bool_t) on by default", "PrintLevel 1 through 3", "Save off by default", "Strategy 0-2 default 1", "EvalErrorWall on by default". NumCPU and Optimize semantics are OUTDATED for the cpu backend; no mention of EvalBackend/BatchMode, Offset, IntegrateBins, RecoverFromUndefinedRegions, MaxCalls (these came later).
- p.9: RooDataHist from TH1 imports binning; default plot error bars are asymmetric Poisson 68% intervals ("classic central", Cousins 1995); `DataError(RooAbsData::SumW2)` gives sqrt(N). Note 6.40 replaces RooHistError::getPoissonInterval by an exact Garwood construction (section 7).
- p.102: weighted unbinned data via setWeightVar; binned weights carry errors (weightError). Relevant to the "weighted data" warning (8.6).
- p.128 `EvalErrorWall`, `PrintEvalErrors` documented here - the origin of the message block in section 8.
- Chapters 4-9: read in the final pass, see 3b.

### 3b. Chapters 4-9 of the v2.91 manual, against 6.36.10 (final pass, 15 October 2026)
The manual was downloaded again to `scratch/study-final-010708/manual/dl/manual.pdf` (134 pages, 3828591 bytes) and its text extracted to `manual/manual.txt` with pypdf (`ext.py`). PDF page numbers equal the printed page numbers. Chapters 4 (p.29-36), 7 (p.66-87) and 9 (p.97-109) were read in full. For chapters 5 (p.37-48), 6 (p.49-65) and 8 (p.88-96) I read the section headings and skimmed the text: convolution, multi-dimensional models and discrete observables do not occur in the project's one-dimensional binned fits. Three statements were checked by running `manual/mcheck.cpp` (output `manual/out-mcheck.txt`).

What bears on the project:
- **p.99, TH1 import adjusts the observable's range outward to bin edges.** The manual says that when the RooRealVar range does not fall on a bin edge of the imported histogram, "the bin that contains the range limit is fully imported and the range limit on the corresponding RooRealVar is adjusted outward". This is still true in 6.36.10 [verified, `out-mcheck.txt` (1)]. A variable [1.29,1.36] imported from 100 bins over [1.25,1.40] becomes [1.289,1.361], with the INFO line `RooDataHist::adjustBinning(dh): fit range of variable x expanded to nearest bin boundaries: [1.29,1.36] --> [1.289,1.361]` [source `RooDataHist.cxx:666-720`]. This is the mechanism behind the Xi fit range found in note 05 ([1.289,1.361] instead of [1.29,1.36]; also notes 04 and 12). It is documented behaviour, not a bug. The observable passed to `RooDataHist` is changed in place, so every later integral and plot of the project uses the widened range [inferred from the run].
- **p.72, a named range that was never defined is "defined on the fly as a range equal to the full range".** Still true, and silent [verified (2)]. `getMin("nope")`/`getMax("nope")` return the full range [0,10]. `createIntegral(..., Range("nope2"))` of a normalised Gaussian returns 1.000000000, and afterwards `hasRange("nope2")` is true. For the project: a misspelt or unset range name in `ExtractYieldsAndPurity` (`signalRegion`, `sidebandRegion`) would give the full-range integral with no message, i.e. a purity computed over the whole fit range. Today the code sets both ranges right before it integrates them (`DynamicRooFitter.h:127,153`) [source], so the case does not occur.
- **p.71, "No consistency checks are performed when multiple ranges are specified" (overlapping ranges double count): OUTDATED.** In 6.36.10, `fitTo(..., Range("a,b"))` and `createIntegral(..., Range("a,b"))` with overlapping ranges both throw: `integrating with respect to the variables (x) on the ranges "a,b" is not possible because the ranges are overlapping` [verified (3); source `RooAbsReal.cxx:563`, `RooFitImplHelpers.cxx:69` `checkIfRangesOverlap`]. The project uses a single range per integral.
- p.70-71: `fitTo(Range(...))` creates the internal ranges `fit_nll_<pdf>_<data>_<range>` (seen in the INFO lines of the run), and a later `plotOn` draws only in the fitted ranges unless `Range()`/`NormRange()` say otherwise. This is still accurate; the project fits the full range, so it does not matter.
- p.102-103: binned datasets carry weight errors (`weightError(RooAbsData::SumW2)` or `Poisson`). Footnote 28: in a weighted ML fit the reported error scales with the sum of the weights, "which is in general incorrect". This is the phi online-efficiency case of notes 05/06 (non-integer contents; `SumW2Error(true)` corrects the errors). Still accurate. Chapter 12, which the manual points to for weighted fits, is a stub in v2.91.
- p.109: "Binned datasets are by construction weighted, so every binned dataset is a weighted dataset". This is why RooFit prints its weighted-data warning for any `RooDataHist` with non-integer contents (note 05, 8.6 here). `numEvents()`/`sumEvents()` in the manual are now `numEntries()`/`sumEntries()` [source `RooAbsData.h:146-152`]: the names are OUTDATED.
- p.29: "The use of Chebychev polynomials over regular polynomials is recommended because of their superior stability in fits" (lower correlations between the coefficients). This supports the project's choice of `RooChebychev` for the K0S/Xi/pion backgrounds. The manual says nothing about a Chebychev sum being able to go negative (note 01, 9.2 here).
- p.33-34: `RooGenericPdf` is normalised "through numeric integration", and "if your formula expression becomes more complicated ... you should write a compiled class". Both still apply to the phi backgrounds `BkgSourav1/2` and `BkgMattia` (`RooGenericPdf`, numeric normalisation; note 04). The custom-class route has a persistence cost (note 01, Third pass: a workspace with a custom class is not self-contained). `RooClassFactory`, which writes such classes, still exists (`roofitcore/inc/RooClassFactory.h`) [source].
- p.30: the Crystal Ball is `RooCBShape` in the manual. The project's double-sided `RooCrystalBall` (6.24+) is not in the manual: OUTDATED by omission (note 01).
- Chapter 5 (convolution) [doc, skimmed]: FFT (`RooFFTConvPdf`), plain numeric (`RooNumConvPdf`) and analytical convolution with resolution models. The project's Voigtian is a dedicated class (`RooVoigtian`, a Breit-Wigner convolved with a Gaussian, p.30), so none of this is needed. A Breit-Wigner ⊗ DSCB would need `RooFFTConvPdf` [inferred].
- Chapters 6 and 8 (multi-dimensional models, discrete observables): nothing bears on the project's one-dimensional fits. `plotOn(..., NumCPU(n))` for Monte Carlo projections (p.84) concerns multi-dimensional projections only.
- Also OUTDATED throughout: `Double_t`/`Int_t`/`kTRUE` (now `double`/`int`/`true` in the 6.36 interfaces) and raw-pointer returns: in 6.36 `reduce` and `generate` return `RooFit::OwningPtr` [source `RooAbsData.h:70-72`, `RooAbsPdf.h:57-62`]; `createProjection` still returns a raw `RooAbsPdf*` (`RooAbsPdf.h:178`).
The quick-start PDF (roofit_quickstart_3.00.pdf) is NOT POSSIBLE to summarise from text: its pages are figures, and text extraction gives only formulas (second pass). Reading it would need OCR, which this environment does not have.

### 5.1 batchcompute.md (author E. Michalainas, September 2021)  [doc]
- Says the library is "still at an experimental stage" (the text predates the 6.32 default switch; it is outdated on this point) and that its purpose is to compute whole data arrays ("batches") per call with auto-vectorisation, compiled for several vector ISAs with the best one chosen at run time; claims "a speedup of 3x-16x" (for unbinned fits with many events; no statement for few-hundred-bin fits).
- User-facing text is outdated: it documents `fitTo(data, BatchMode("cpu"))` / `BatchMode("cuda")` (in 6.36 this is `EvalBackend("cpu"|"cuda")`; `BatchMode` is deprecated per RooAbsPdf.cxx and does not compile in this build per note 03). Multithreading is described through `ROOT::EnableImplicitMT(nThreads)` before `fitTo`. [doc] Whether this works for the 6.36 backend was NOT tested; since ROOT 6.36.10 `NumCPU` is ignored by the cpu backend (RooAbsPdf.cxx:835) and a NumCPU-driven multi-threaded batch evaluation was only merged to master on 2026-09-08 (PR #23140, section 9.8), it is [inferred] that the old EnableImplicitMT route is not an effective way of speeding up 6.36 fits.
- Describes the user-pdf hook `RooAbsReal::computeBatch(...)` (must fill `output[]` with NORMALISED probabilities) and says the "easiest way" to get a class accelerated is to request it on GitHub. It names `RooFitDriver`, which in 6.36 is the `RooFit::Evaluator` (the name is out of date). RooBatchCompute reports "generic CPU library compiled with no vectorizations" on this macOS arm64 build [verified in note 08 section 6 run of rf202], which is consistent with #18738 (section 9.7).

### 5.2 test_statistics.md (P. Bos, December 2021, updated October 2024)  [doc]
- Describes `RooFit::TestStatistics`: statistics classes (`RooAbsL` with `RooBinnedL`, `RooUnbinnedL`, `RooSubsidiaryL`, `RooSumL`, built by `NLLFactory`) separated from calculators (`LikelihoodSerial`, `LikelihoodJob`, `LikelihoodGradientJob`). The parallel calculators need `RooFit::MultiProcess` (fork + ZeroMQ), which is not built here (note 06).
- Statement on offsetting (quotable): "Offsetting is a feature of calculation in a fitting context; it enhances numerical precision by subtracting the initial likelihood value from the value that the minimizer sees, thus setting it to zero for the minimizer. Since this does not impact the derivative terms, it does not affect the fitting result, except for added numerical precision." In the `TestStatistics` API it is `RooMinimizer::setOffsetting(true)`; with `fitTo` it is `Offset(true)`. [doc] This is the developer-level statement of why `Offset` helps when |NLL| is large (cf. 9.1).
- Caveat quoted: results are the same as the old classes except for simultaneous pdfs with constraint terms when offsetting is on. Not relevant to the project's single-pdf fits [inferred].
- `ConstantTermsOptimizer` / `m.optimizeConst(2)` are the `TestStatistics` equivalents of const-term optimisation (cf. note 06: no-op for the cpu backend).
- Load-balancing section (number of workers N_w plus two helper processes, event versus component splitting, task priority queue, `TimingAnalysis`) applies to MultiProcess only; the project cannot use it (note 06).

### 5.3 roofit_hs3.md (C. Burgard, March 2023)  [doc]  (RooFitHS3 is also the subject of note 02)
- Library "still at an experimental stage"; backend is the builtin nlohmann JSON; the RapidYAML backend was dropped ("YML users could use YML to JSON converters"). Main class `RooJSONFactoryWSTool`.
- "Open-world" philosophy: feature-complete serialisation "will probably never be fully achieved", so users are expected to add importers and exporters for their own classes.
- Two registration mechanisms. (a) Proxy-based, no C++: an entry in a JSON file of EXPORT KEYS (`"<C++ class>": {"type": "<json-key>", "proxies": {"<proxy name>": "<json key>"}}`) usable when the class has only proxies as members, and an entry in a JSON file of FACTORY EXPRESSIONS (`"<json-key>": {"class": "<C++ class>", "arguments": ["<key>", ...]}`) usable when all members are constructor arguments. Custom files are loaded with `RooFit::JSONIO::loadExportKeys(file)` and `RooFit::JSONIO::loadFactoryExpressions(file)`. (b) Custom C++ classes deriving from `RooFit::JSONIO::Importer` (`importFunction` / `importPdf`) and `Exporter` (`key()`, `exportObject`), registered with `registerImporter(key, new X, topPriority)` and `registerExporter(Class, new Y, topPriority)`. Native implementations take precedence over proxy-based ones; several importers can exist for one key and are tried in priority order.
- [verified in this pass, section 9.9 below and note 07] the proxy-based route works for `RooChebychev` in this build with two 1-line JSON files (no C++), export and import round trip: the NLL is identical to 12 digits.
- Asks users to contribute missing importers/exporters to ROOT as pull requests.

### 5.4 roofit_ad.md (October 2023)  [doc]
- Explains that AD support (Clad) requires C++ code generation: a `CodegenContext` visits the computation graph through `RooFit::codegenImpl(RooAbsArg&, CodegenContext&)`; `RooFuncWrapper` JIT-compiles the generated code with the ROOT interpreter, generates the gradient with Clad and compiles that too; the wrapper is a drop-in replacement for the top node and can be queried for the gradient. Math is moved into free functions in `MathFuncs.h` because "Clad prefers the code for models to be within a single translation unit".
- States plainly: "The initiative to add AD support / Code Generation has been started, but has not yet achieved full coverage for the models defined/maintained in RooFit" and "classes using Numerical Integration" cannot support AD "so far, no" (Appendix A). Compile time: "an area of research that still needs some work. In most cases, the compile times are reasonable, but with an increase in the level of complexity, higher compile times may be encountered."
- Appendix A: a class that calls external Math functions without a registered derivative falls back to numeric differentiation for THAT function only. A recipe with `analyticalIntegral()` and `buildCallToAnalyticIntegral()` shows how a class gets integral support in generated code.
- [verified, note 06 section Codegen and AD] consequences for the project: `RooCrystalBall` and `RooVoigtian` have no `codegenImpl` (coverage list from `CodegenImpl.cxx`, in note 06, section Codegen and AD), so the DSCB models cannot use `EvalBackend("codegen")`.

### 9.1 Minuit2 status 3 ("Edm is above max") with extended binned fits: what the developers say
There is NO GitHub issue titled or about "status 3 with extended binned fits" (searches for `Minuit2 edm`, `"Edm is above max"`, `RooFit status 3`, `machine accuracy` returned only the items below). The developer position is in forum answers by Lorenzo Moneta (Minuit2/ROOT::Math author) and in tutorial code by Jonas Rembser:
1. Meaning of the codes (Moneta, 2013-08-14, https://root-forum.cern.ch/t/meaning-of-values-returned-by-roofitresult-status/16355): for Minuit2 status 0 OK, 1 covariance was made pos. def., 2 Hesse invalid, 3 "Edm is above max", 4 reached call limit, 5 any other failure; "If you run also Hesse and/or Minos the status will be updated." [doc] (Consistent with note 03, [source].)
2. Cause (Moneta, 2015-12-07, https://root-forum.cern.ch/t/edm-is-above-max/20301): "This failure is typically caused by bad precision in computing the function to minimise." [doc]
3. Large statistics (Moneta, 2020-07-01, https://root-forum.cern.ch/t/minuit-fit-problem-with-large-statistics/40176): "with large statistics, if doing a binned fit you could have numerical problems when computing the likelihood ... The issue is not in Minuit but in the function that is provided to Minuit to minimize"; he recommends summing mu - n log(mu) per bin directly (not mu - n + n log(n/mu)) and Kahan summation (`ROOT::Math::KahanSum`). [doc] [source] the 6.36 cpu backend does use Kahan sums (RooBatchCompute.cxx:266,276; RooNLLVarNew.cxx:217) so that part is already in place here.
4. The machine limit (Moneta, 2023-04-13, https://root-forum.cern.ch/t/warning-in-minuit2-variablemetricbuilder-reached-machine-accuracy-limit/54379): "The machine limit ... is computed as epsilon * nll_value, where epsilon is a precision parameter of Minuit2 (it can be changed using SetPrecision) and it is around 1E-8. If you are using the RooFit Offset option, the overall nll_value will be smaller and then also your machine limit." Recommendation given to the user: add `Offset(true)` to `fitTo`; the user reported the warning disappeared. [doc]
5. Same advice, 2021-10-19 (https://root-forum.cern.ch/t/minuit2-machine-accuracy-limit-reached/47302): the user already used `Extended(True), SumW2Error(True), Strategy(2)` and still hit "reached machine accuracy limit". Moneta: "You can change the tolerance in RooFit only if you use the RooMinimizer interface for fitting instead of fitTo ... However the problem is probably caused by a numerical error in evaluating your likelihood. You can try to mitigate it by using the option Offset(true) or a better parametrisation of your model causing less numerical error. Also be sure you are using everywhere double precision and not floats. If your model contains histograms make sure you are using TH1D objects instead of TH1F." Outcome: "adding the Offset(true) fixed the issue". [doc] Note the point for the project: Strategy(2) did not help in that case.

### 9.2 Chebychev going negative; "p.d.f value is less than zero, trying to recover"; RecoverFromUndefinedRegions
- GitHub #12452 "[RF] Handling of the negative values in RooChebychev causes fit divergence" (opened 2023-03-08 by Bilokin, closed after the 2025-08-27 to 2025-10-15 exchange (final closure 2025-10-14 per the API); https://github.com/root-project/root/issues/12452). Second-order RooChebychev goes negative near c1=-0.5, c2=-0.55 on [0.47,0.53]; the reporter says ROOT 6.20 clipped negative values to zero and 6.24 sets them differently, which made some fits diverge. Explanation by ferdymercury (2025-03-20): the polynomial is 1 + c1 x' + c2 (2x'^2 - 1) on the rescaled variable x' in [-1,1]; here it is negative for x' > 0.98; "to ensure avoiding negative values in the whole range, one would need to set coeffs[0] + coeffs[1] > -1" (i.e. the value at the upper edge, 1 + c1 + c2, positive). guitargeek (J. Rembser, 2025-08-27): "while clipping the values to zero seems to be useful for the plot, it is not useful when using it in a fit. If the pdf is evaluated where it is zero, the NLL will be NaN again anyway", so restricting the plot range is the right way. The claimed fit-convergence regression could not be verified: "no reproducer of the fit was provided"; on 2025-10-14 ferdymercury posted a toy reproducer, "checked with master and 6.36.02 and the fit converges". [doc] (Note: the edge condition quoted is one necessary condition; negative values also occur at x'=-1 (1 - c1 + c2 < 0) and, for c2 > 0, in the interior.) ### 9.4 "weighted data" warning; SumW2Error and AsymptoticError semantics
- Warning text and trigger: section 8.5 [source] (FitHelpers.cxx:500-515). The warning itself says the parameter values "will always be calculated taking the weights into account"; only the ERROR estimate is a choice.
- Developer statements: rf403 tutorial (local): "A plain Maximum likelihood fit to weighted data does in general NOT result in correct error estimates, unless individual event weights represent Poisson statistics themselves"; first-order correction V' = V C^-1 V (V from -sum w log f, C from -sum w^2 log f) is `SumW2Error(true)`. PR #14751 (Langenbruch, merged 2024-05-22, https://github.com/root-project/root/pull/14751): extended term added to the asymptotically correct method (6.32); body says "Added warning in case of binned fits. In this case a chi2 fit using the std. treatment of weights should be preferable." [doc] [source] the warning exists in 6.36.10: FitHelpers.cxx:84-85 "Asymptotic error correction is requested for a binned data set. This method is not designed to handle binned data. A standard chi2 fit will likely be more suitable." [verified, printed in my run below].
- Known open problems: GitHub #11660 "[RF] Issues when using RooFit::AsymptoticError for weighted likelihood fits" (opened 2022-11-04 by Moneta, STILL OPEN; large errors reported at https://root-forum.cern.ch/t/very-large-errors-when-using-roofit-asymptoticerror/52003; numerical instabilities of the derivatives, ROOT-10866); #11112 (unweighted data with `SumW2Error`/`AsymptoticError` giving different errors; closed 2024-05-22: "the reason for this inconsistency was that the fit was actually failing" (non positive-definite covariance), per PR #14751 text); #12935 global correlations after SumW2Error (6.34); #12453 weight errors wrong after splitting RooDataHist (6.30). [doc]
- [verified, this pass] numeric semantics on a REAL k0s cell (mult0, pT33, N=107148, DSCB+Chebychev1; histogram scaled by a constant weight w with Sumw2 stored, so the correct error of nsig is w times the unweighted one = w x 462.5; all fits `Offset("bin")`, status 0; program `study060708/w.cpp`, output `wtest.out`):
  | w | default | SumW2Error(true) | SumW2Error(false) | AsymptoticError(true) | correct |
  |---|---|---|---|---|---|
  | 1 | 462.5 | 465.0 | 462.5 | 458.4 | 462.5 |
  | 0.37 | 280 | 170.5 | 280 | 167.8 | 171.1 |
  | 3 | 799.6 | 1386 | 799.6 | 1369 | 1387.5 |
  (errors on nsig). So the default and `SumW2Error(false)` give the error "as if the dataset had sum(w) events" (here sqrt(w) x 462.5), which is wrong by sqrt(w) for scaled data; `SumW2Error(true)` is right to 0.1-0.6%; `AsymptoticError(true)` within 2% and prints the "not designed to handle binned data" warning for a RooDataHist. The truth of the stored errors (that Sumw2 was filled with the proper w^2) must hold [inferred]. For histograms WITHOUT Sumw2 `RooDataHist` takes the weight-squared as the content [inferred; not tested here].

### 9.5 Bin-centre evaluation in binned fits (bias) and what the developers did
- Gligorov, Hageboeck, Nanut, Sciandra, Tou, "Avoiding biases in binned fits", arXiv:2104.13879 (28 April 2021, revised 14 June 2021): "For many years the widely used statistical modelling package RooFit evaluated probabilities at the bin centre, leading to significant biases for strongly curved probability density functions. We demonstrate the biases with real-world examples, and introduce a PDF class to RooFit that removes these biases." [doc: https://arxiv.org/abs/2104.13879, abstract only; the class is `RooBinSamplingPdf`, enabled by `IntegrateBins(precision)`, as in rf614 and PR #6694 "[RF] Implement finer sampling of PDF in binned fits" (2020), https://github.com/root-project/root/pull/6694].
- [verified, this pass, note 06 section Bin-centre versus integrated-bin] on Asimov data built from the project's own k0s fits: centre evaluation shifts nsig by -7.6e-4 relative (-2.55 sigma) at nsig=2.25e7 (cell 3,10) and -2.6e-4 (-1.5 sigma) at 3.9e7 (cell 5,8), by at most 0.42 sigma in the other three cells (6e6 to 1.7e7), and by at most 0.26 sigma at 1% of that statistics; IntegrateBins removes the shift (all pulls <= 0.02 sigma).
- #22598 (open, 2026-06-13, kratsg, https://github.com/root-project/root/issues/22598): an HS3 consumer cannot tell whether a continuous pdf paired with a binned dataset is evaluated at the bin centre or integrated over the bin; the issue asks for this to be recorded in the file. cburgard: "the last years @guitargeek has worked a bit on related issues". Open. For the project this means: an HS3 export does not carry the `IntegrateBins` choice (note 02/07).
- PR #23357 (open, 2026-09-14): `RooFit::makeResidHist()`/`makePullHist()` with bin integration (pulls computed from bin-integrated model values rather than the centre value) [doc, title only; not read].
- Developer position on the bin-centre default, in #22598 (guitargeek, 2026-06-15/16) [doc]: "By default, RooFit *always* evaluates the pdf at the bin center when the dataset is binned. If the model is continuous, this is indeed a crude approximation. That's why the integration over bins was introduced later", with two routes, `RooBinSamplingPdf` at the model level ("useful for model serialization in the RooWorkspace") or the `IntegrateBins` option; and: "Maybe now is the time to rectify this presumable historic mistake of the bin center approximation by default". cburgard argues the evaluation scheme belongs to the "engine", not to the HS3 model. State on 2026-10-15: issue open, 7 comments, no decision.
- Developer position on goodness of fit, in #21697 (guitargeek, 2026-03-26) [doc]: `RooPlot::chiSquare()` should be deprecated ("making `RooAbsReal::createChi2()` the one single entry point"; removal only in ROOT 7), "Actually what we want is the Poisson deviance", e.g. a `goodnessOfFit("deviance")` default with `"pearson"` as option, and "per-bin Poisson deviances would also be the right replacement for pulls". The reporter adds that `chiSquare` interpolates the curve at bin centres and returns chi2/ndf by default. Note 07 section (k) computes such a deviance on real cells.
